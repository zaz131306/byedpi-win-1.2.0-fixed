# Почему не открываются сайты, и что исправлено

Разбор по исходникам **byedpi v0.17.3** — ровно той версии, бинарник которой лежит
в `bin/ciadpi-win-x64.exe` (сверено по SHA-256: файл побайтово совпадает с
официальным ассетом `byedpi-17.3-x86_64-w64.zip` релиза `v0.17.3`, так что
«кривая сборка» исключена).

---

## 1. Главная причина: флага `+sh` в byedpi не существует

Проект лечит «HTTP не работает» флагом `+sh`, и это же написано в `README.md`:

| Флаг | К чему привязано правило |
|---|---|
| `+s` | к SNI — только TLS |
| `+h` | к HTTP-заголовку `Host` — только HTTP |
| **`+sh`** | **к тому и другому сразу** ← неправда |

В `main.c` v0.17.3 функция `parse_offset()` разбирает значение так:

```c
if (*end == '+') {
    switch (*(end + 1)) {          /* РОВНО ОДИН символ */
        case 's': part->flag = OFFSET_SNI;  break;
        case 'h': part->flag = OFFSET_HOST; break;
        case 'n': break;
        default:  return -1;
    }
    switch (*(end + 2)) {          /* и РОВНО ОДИН дополнительный */
        case 'e': part->flag |= OFFSET_END;   break;
        case 'm': part->flag |= OFFSET_MID;   break;
        case 'r': part->flag |= OFFSET_RAND;  break;
        case 's': part->flag |= OFFSET_START;
    }
}
part->pos = val;
return 0;                          /* <-- никакой проверки остатка строки */
```

`"1+sh"` → первый символ `s` → `OFFSET_SNI`; второй символ `h` не входит в
`{e,m,r,s}` → **просто игнорируется**; остаток строки в v0.17.3 не проверяется
вовсе и `return -1` не делается.

> **Вывод: `--split 1+sh` ≡ `--split 1+s`. Никакой ошибки ciadpi не выдаёт.**
> Комбинации «SNI + Host» в byedpi нет ни в одной версии.

Дальше в `desync.c`:

```c
static long gen_offset(long pos, int flag, ...)
{
    if (flag & (OFFSET_SNI | OFFSET_HOST)) {
        init_proto_info(buffer, n, info);
        if (!info->host_pos
                || ((flag & OFFSET_SNI) && info->type != IS_HTTPS)) {
            return -1;                    /* <-- для HTTP + флаг SNI */
        }
        pos += info->host_pos;
        ...
```

```c
long pos = gen_offset(part.pos, part.flag, buffer, n, lp, &info);
...
if (pos < 0 || pos < lp) {
    LOG(LOG_E, "split cancel: pos=%ld-%ld, n=%zd\n", lp, pos, n);
    break;                                /* <-- BREAK, не continue! */
}
```

`break` означает, что **одно неприменимое правило отменяет все остальные правила
группы**, стоящие после него. То есть на обычном HTTP:

* `--split 1+s` → `pos = -1` → `split cancel` → `break`
* стоящий следом `--disorder 3+s` даже не рассматривается
* запрос уходит **абсолютно нетронутым**

Это и есть «http/https пакеты вообще не жмёт». При этом прокси выглядит здоровым:
порт слушается, SOCKS5 отвечает, HTTPS-сайты с SNI фрагментируются нормально.

### Что поражено в поставке

Прогон `host/audit_offset_flags.py` (эмулирует `parse_offset`/`gen_offset`/`desync`
и разбиение на группы по `--auto`):

| Пресет | Windows, HTTPS | Windows, HTTP |
|---|---|---|
| `recommended` **(по умолчанию!)** | работает | **ОТМЕНА — `--split 1+s`** |
| `universal` | работает | **ОТМЕНА — `--split 1+sh` ≡ `1+s`** |
| `ladder` | работает | **ОТМЕНА — `--split 1+sh`** (и на Linux тоже) |
| `disorder` | работает | **ОТМЕНА — `--split 1+s`** |
| `http` | работает | работает |
| `fake`, `fake-ttl`, `aggressive` | работает | работает |
| `oob`, `tlsrec` | группа 0 пуста | группа 0 пуста |

Особенно обидно: `universal` и `ladder` — это ровно те два пресета, которые
`ctl.py doctor` советует как лекарство от «HTTPS открывается, а HTTP нет».
Совет не работает, потому что лекарство содержит ту же ошибку.

Кандидаты автоподбора (`host/strategy_candidates.txt`, 60 строк):

* **30 из 53** пригодных для Windows строк на HTTP не фрагментируют ничего;
* 4 строки из 60 содержат недопустимые комбинации флагов (6 вхождений:
  `+sh`×3, `+sn`×1, `+nme`×2) — хвост молча отбрасывается byedpi; из 53
  «windows-пригодных» таких 3;
* правил, реально покрывающих HTTP, во всём файле 8: `+h`×3, `+hm`×2, `+nm`×2,
  `+nr`×1 — и они стоят не в начале строк, а `desync()` делает `break` на первом
  же неприменимом правиле, то есть до них очередь обычно не доходит.

Поэтому `pick --url http://rutor.info/` почти гарантированно отвечает
«ни одна стратегия не пробила блокировку» — перебирать ему нечего.

### Правильный флаг — `+h`

`init_proto_info()` сначала пробует `parse_tls()` (даёт позицию **SNI**), и только
потом `parse_http()` (даёт позицию **значения заголовка `Host`**):

```c
if ((info->host_len = parse_tls(buffer, n, &host)))       info->type = IS_HTTPS;
else if ((info->host_len = parse_http(buffer, n, &host, 0))) info->type = IS_HTTP;
info->host_pos = host ? host - buffer : 0;
```

Проверка на «не тот протокол» в `gen_offset()` есть **только для `OFFSET_SNI`**.
Значит `+h`:

* на TLS → `host_pos` = позиция SNI, поведение **идентично** `+s`;
* на HTTP → `host_pos` = позиция имени в `Host:`, правило **применяется**.

`+h` — строгий надмножество `+s`. Замена `+s` → `+h` не может ухудшить HTTPS
и чинит HTTP. Именно это сделано в сборке.

## 2. Что делать прямо сейчас (без замены файлов)

Одна команда в каталоге проекта:

```bat
python host\ctl.py set strategy=custom "custom_args=--split 1+h --disorder 3+h --auto=torst --timeout 3 --tlsrec 1+s"
```

Прокси перезапустится сам. Проверка:

```bat
python host\ctl.py doctor --url rutor.info,instagram.com
python host\ctl.py selftest
```

`doctor` без схемы проверяет домен **обоими** протоколами — это и есть нужный тест:
раньше HTTPS проходил, а HTTP падал; теперь должны пройти оба.

Откат:

```bat
python host\ctl.py set strategy=recommended
```

## 3. Как увидеть ошибку своими глазами

`LOG_E` в byedpi равен `-1`, а макрос печати — `if (params.debug >= s)`. То есть
`split cancel` печатается **даже при `debug=0`** и уже сейчас лежит в вашем журнале:

```bat
python host\ctl.py logs -f
```

ищите строки

```
split cancel: pos=0-18, n=431
```

Каждая такая строка на HTTP-запросе — это ровно тот сайт, который не открылся.
Для подробного разбора:

```bat
python host\ctl.py set advanced.debug_level=1
```

(после диагностики верните `advanced.debug_level=0` — на уровне 1 журнал очень
многословен).

## 4. Отдельно про Instagram и YouTube

Это **другие** проблемы, флаг `+h` их не лечит.

### Instagram (и вообще HTTPS, который не открывается напрочь)

`--split 1+s --disorder 3+s` — это рекомендованная автором byedpi связка для
Windows, и на части провайдеров её достаточно. Если не хватает — порядок такой:

```bat
:: 1. лестница из четырёх групп (ciadpi перебирает сам по триггеру torst)
python host\ctl.py set strategy=ladder

:: 2. фейковый ClientHello, гаснущий по TTL
python host\ctl.py set strategy=fake-ttl

:: 3. автоподбор по РЕАЛЬНО заблокированному сайту
python host\ctl.py pick --url https://www.instagram.com/ --apply -y
```

Важно про `pick`: сайт-проба обязан быть **заблокированным у вас**. Подбор на
`example.com` бессмысленен — он открывается и без обхода, поэтому победит первая
же попавшаяся строка.

Если `pick` перебрал всех и не нашёл ничего — значит ваш фильтр режет не по
содержимому пакета, а по IP-адресу назначения (или по TLS-отпечатку).
Десинхронизацией это не обходится **в принципе**. Тогда остаётся
`transport=tunnel` — WSS-туннель до собственного шлюза, он в проекте есть
(`tunnel/`, см. `tunnel/README.md`), но требует свой сервер с доменом.

### YouTube «еле-еле»

Три вещи, которые надо проверить по порядку:

1. **HTTP/3 должен быть выключен.** QUIC мимо SOCKS5 не ходит. `install.bat`
   пишет в `user.js` профиля `network.http.http3.enable=false`, но `user.js`
   читается **только при старте Firefox** — нужен один полный перезапуск браузера
   (закрыть все окна, не «перезагрузить вкладку»). Проверка:
   ```bat
   python host\ctl.py doctor
   ```
   строка `HTTP/3` должна быть `off`; `pending_restart` — значит браузер ещё не
   перечитал `user.js`.
2. **Firefox действительно смотрит в прокси.** `doctor` показывает
   `network.proxy.type` (должно быть `1`) и `SOCKS в настройках` (`127.0.0.1:1080`).
   Если `type` не задан — расширение не достучалось до native-хоста, трафик идёт
   напрямую и никакая стратегия ни на что не влияет.
3. **Версия SOCKS = 5.** ciadpi понимает только v5; с v4 он отвергает каждое
   соединение. В попапе поле «Версия SOCKS», в конфиге `socks_version`.

Тормоза YouTube в РФ — это шейпинг полосы, а не блокировка; он лечится только
подбором стратегии под провайдера (`pick --url https://www.youtube.com/`).

## 7. Коротко, если читать только это

1. `+sh` — несуществующий флаг, byedpi молча читает его как `+s`.
2. `+s` на HTTP → `gen_offset()` возвращает −1 → `desync()` делает `break` →
   запрос уходит нефрагментированным. Отсюда мёртвый rutor.info.
3. Лечение — флаг `+h`: он покрывает и TLS, и HTTP.
4. Одна команда: `python host\ctl.py set strategy=custom "custom_args=--split 1+h --disorder 3+h --auto=torst --timeout 3 --tlsrec 1+s"`
5. Instagram/YouTube — отдельная история: `ladder` → `fake-ttl` → `pick` по
   заблокированному сайту; YouTube дополнительно требует выключенного HTTP/3
   и полного перезапуска Firefox.

## 8. «CERTIFICATE_VERIFY_FAILED ... unable to get local issuer certificate»

Отдельный вопрос, который выглядит страшнее, чем есть.

```
✘ запрос https://example.com/ — не удалось проверить сертификат:
  [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
  unable to get local issuer certificate (_ssl.c:1032).
  Хранилище CA не пустое (63 корней), так что дело не в них: сайт отдаёт
  цепочку без промежуточного сертификата либо TLS-собеседник подменён.
```

### Это не про прокси — вообще

`SSLCertVerificationError` возникает внутри `ctx.wrap_socket(...)`, то есть
**после** того как `socks5_connect()` успешно отработал. К этому моменту ciadpi
уже принял CONNECT, разрешил имя, открыл восходящее TCP-соединение и передал
байты в обе стороны. SOCKS5-прокси работает на уровне байтов и **физически не
может** ни подменить сертификат, ни укоротить цепочку.

Если бы ломался обход DPI, ошибка была бы другой: `SSLEOFError`,
`WRONG_VERSION_NUMBER`, `tlsv1 alert`, таймаут или `[WinError 10054]` — но не
`CERTIFICATE_VERIFY_FAILED`.

На Firefox это не влияет никак: у браузера собственный набор корневых
сертификатов (NSS) и собственный TLS-стек.

### Реальная причина: `example.com` — плохая тестовая цель

`example.com` с 2025 года обслуживается Cloudflare и отдаёт такую цепочку:

```
example.com
  └─ Cloudflare TLS Issuing ECC CA 3      (O = SSL Corporation)
       └─ SSL.com TLS Transit ECC CA R2
            └─ AAA Certificate Services   ← корень Comodo от января 2004 года
```

Mozilla Root Store Policy v2.9 (сентябрь 2023) ввела ограничение в 15 лет на
срок жизни ключевого материала корневого CA. `AAA Certificate Services` вышел
за него на много лет, и его TLS-trust бит был помечен как **distrusted после
15 апреля 2025**. Из свежих наборов корень удалён.

Браузеры выкручиваются **AIA-chasing**: наткнувшись на неподходящий корень,
Firefox находит альтернативный путь через `SSL.com TLS ECC Root CA 2022` и молча
использует его. **OpenSSL и Python AIA не делают** — они валидируют только то,
что прислал сервер, плюс локальное хранилище. Отсюда `verify_code = 20`
(`UNABLE_TO_GET_ISSUER_CERT_LOCALLY`) на ровном месте.

Дополнительно на Windows: Python берёт корни из хранилища Windows, но — в
отличие от самой Windows — **отсутствующие корни по сети не докачивает**.
63 корня вместо ~140 — это как раз неполное хранилище.

### Что в этом сообщении было неправдой

Фраза «Хранилище CA не пустое (63 корней), так что дело не в них: сайт отдаёт
цепочку без промежуточного сертификата либо TLS-собеседник подменён» — вывод
неверный. Непустое хранилище **не означает**, что в нём есть *нужный* корень.
Из двух предложенных причин (обрыв цепочки / подмена) ни одна не является
наиболее вероятной, а третья — неполное хранилище — даже не рассматривалась.

Хуже другое: откатная проверка в `selftest` (HTTP-запрос + TLS без проверки
сертификата) запускалась **только при `ca_problem`**, а `ca_problem`
устанавливался лишь когда корней `== 0`. При 63 корнях откат не срабатывал,
`selftest` объявлял прокси нерабочим и замолкал — то есть ровно тот инструмент,
который должен был сказать «прокси в порядке», говорил обратное.

### Исправлено

| Файл | Что |
|---|---|
| `host/netutil.py` | любой `SSLCertVerificationError` теперь ставит `cert_problem`, а не только `ca_problem`; текст сообщения не делает неподтверждённых заявлений; добавлен автоматический повтор запроса с корнями Mozilla из `certifi` — если с ними проходит, так и сообщается |
| `host/proxy_core.py` | откатная ветка `selftest` (HTTP + TLS без проверки) срабатывает при **любой** ошибке сертификата, а не только при пустом хранилище; в итоговом тексте больше нет утверждения «у Python нет CA-корней» |
| `host/config.py` | `test_url` по умолчанию: `https://example.com/` → `https://www.google.com/` (чистая цепочка Google Trust Services → GTS Root R2, есть во всех хранилищах) |
| `host/ctl.py` | `doctor` берёт контрольный сайт из `test_url`, а не из зашитого `example.com`; `selftest` печатает подсказку про `check_tls.py` |
| `host/check_tls.py` | **новое** — решающая диагностика, см. ниже |

Если в вашем `config.json` уже записан `example.com`, поправьте:

```bat
python host\ctl.py set test_url=https://www.google.com/
```

### Как убедиться за 30 секунд

```bat
python host\check_tls.py
```

Скрипт прогоняет одно и то же рукопожатие в четырёх комбинациях —
напрямую / через прокси × системное хранилище / certifi — и печатает, **каких
именно корневых CA не хватает** в хранилище Python (сравнением с набором
certifi/Mozilla).

| Что показал скрипт | Значит |
|---|---|
| FAIL и напрямую, и через прокси | прокси не при чём. Ставьте `pip install certifi` или обновите хранилище Windows |
| OK напрямую, FAIL через прокси | единственный расклад, где прокси подозревается — проверьте `set strategy=plain` |
| с certifi OK, без него FAIL | неполное системное хранилище, лечение — `pip install certifi` |
| «через прокси / без проверки» = OK | TLS сквозь обход DPI ходит; канал и стратегия работают |

Отдельно посмотрите на строку `издал:` — если там имя вашего антивируса
(Kaspersky, ESET, Sophos, Zscaler), TLS перехватывается локально, и это тоже не
имеет отношения к ciadpi.

### Лечится одной командой

```bat
pip install certifi
```

`netutil.ssl_context_for_verify()` подхватывает certifi и раньше, но только
когда системное хранилище **пустое**. Теперь повтор с certifi выполняется и при
неполном хранилище.

## 9. Автоподбор: почему один `pick` не может починить все сайты

`ctl.py pick` находит работающий набор аргументов и сохраняет его как
**глобальный** `custom_args`. ciadpi применяет его ко всем соединениям сразу.
Поэтому «YouTube открылся, а rutor и Instagram нет» — это не сбой подбора, а
его штатный результат: рабочая комбинация у каждого сайта своя, и одна строка
физически не может быть оптимальной для всех.

Отдельно: подбор по `https://rutracker.org/` (сайт по умолчанию) вообще ничего
не говорит про `http://rutor.info/` — это разные протоколы, и до исправления
раздела 1 большинство кандидатов HTTP не фрагментировали в принципе.

### Что умеет byedpi и чего не использовал проект

byedpi назначает разные параметры разным доменам. Всё проверено по исходникам
v0.17.3:

| Опция | Как работает | Где |
|---|---|---|
| `--hosts <file\|:str>` | ограничивает группу списком доменов; `:строка` — inline, разделители пробел/перевод строки | `main.c: ftob()`, `parse_hosts()` |
| совпадение домена | **точное или по поддомену**: `host_cmp()` сравнивает строки с конца и считает совпадением равенство либо точку перед общим суффиксом. Записи `rutor.info` достаточно для `www.rutor.info`. Звёздочки не поддерживаются, только строчные буквы | `mpool.c: host_cmp()`, `main.c: lower_char()` |
| `--proto <t,h,u,i>` | ограничивает группу протоколом: `t` = TLS ClientHello, `h` = HTTP | `extend.c: check_proto_tcp()` |
| `--auto=none` | начинает новую группу с пустым триггером — группа всегда подходит, если совпали `hosts`/`proto` | `main.c: case 'A'` |
| порядок | группы перебираются слева направо, побеждает **первая** подходящая | `extend.c: setup_conn()` |

Две вещи, о которых обязательно надо знать:

1. **Соединение, не подошедшее ни одной группе, не идёт напрямую — оно
   дропается.** `setup_conn()` в этом случае печатает `drop connection` и
   возвращает −1. byedpi сам добавляет пустую неограниченную группу, если
   ограничены все (`all_limited` в `main.c`), но последняя группа без
   `--hosts` в строке должна быть всегда — она же задаёт поведение для всех
   остальных сайтов.
2. **`--hosts` в группе действует только до следующего `--auto`.** Если
   подобранный набор содержит свой `--auto=torst`, вторая подгруппа окажется
   неограниченной и будет применяться ко всем сайтам подряд. Поэтому при
   склейке `--hosts`/`--proto` надо повторять в каждой подгруппе — именно это
   делает `regroup()` в `pick_multi.py`.

### Новый инструмент: `host/pick_multi.py`

```bat
python host\pick_multi.py --url http://rutor.info/ ^
                          --url https://rutor.info/ ^
                          --url https://www.instagram.com/ ^
                          --url https://www.youtube.com/ ^
                          --apply -y
```

Что он делает:

1. прогоняет кандидатов **отдельно по каждому URL** (URL со схемой — поэтому
   `http://` и `https://` одного домена подбираются независимо и попадают в
   разные группы через `--proto`);
2. берёт самого быстрого победителя на сайт;
3. склеивает всё в одну строку: по группе `--hosts :домен [--proto t|h]` на
   каждый сайт, повторяя ограничения после каждого `--auto` внутри набора,
   и замыкает строкой группы по умолчанию без `--hosts`;
4. применяет её и **перепроверяет все сайты уже на склеенной строке** — это
   обязательный шаг, потому что составная командная строка может вести себя
   не так, как каждый набор по отдельности.

Без `--apply` настройки возвращаются, а строка печатается в виде
JSON-литерала — её можно вставить в `config.json` в поле `custom_args`.

Ключи: `--stop-after N` (сколько успешных на сайт, по умолчанию 1),
`--limit N`, `--timeout`, `--dump файл`, `-y`.

### Порядок кандидатов для HTTP-адресов

Для `http://`-адреса список кандидатов сначала сортируется: те, у которых
правила привязаны только к SNI (`+s`) и потому на обычном HTTP не
фрагментируют ничего, уезжают в конец. Проверка делает ровно то же, что
`parse_offset()` → `gen_offset()` → `desync()` в byedpi v0.17.3, — код взят из
`audit_offset_flags.py`. Ничего не отбрасывается: сортировка устойчивая, при
достаточном `--limit` будут попробованы и они.

Смысл не в скорости, а в результате. Без сортировки `--limit 20` на
`http://rutor.info/` мог целиком уйти на заведомо мёртвые строки и выдать
«ни один кандидат не сработал» там, где рабочий кандидат просто стоял 30-м.

Текущий расклад по `strategy_candidates.txt` (Windows-сборка):

```
всего пригодных кандидатов : 66
HTTP не фрагментируют      : 30   <- после сортировки идут последними
с молча отброшенным хвостом: 0    <- +sh / +sn / +nme больше нет
```

Позднее сортировка была зашита прямо в файл, а не только в `pick_multi.py`, —
см. раздел 12: там же про дефолт ByeByeDPI x tg, который встал первым
кандидатом. Итог: первые 36 пригодных на Windows кандидатов живы для HTTP.

### Заодно исправлен разбор кавычек на Windows

`strategies.parse_custom()` использовал `shlex.split(text, posix=False)` на
Windows — чтобы не портить обратные слэши в путях. Побочный эффект: в
непозиксном режиме shlex **не снимает кавычки**. Токен `":a b"` доезжал до
ciadpi вместе с кавычками, `ftob()` не видел двоеточия первым символом и
пытался открыть файл с кавычками в имени — процесс падал с `read/parse`, порт
не поднимался. То есть любое значение с пробелом в кавычках
(`--hosts`, `--fake-data`, `--ipset`) на Windows было неработоспособным.

Добавлен `strategies.split_args()`: кавычки снимаются, обратные слэши
сохраняются. Работает одинаково на всех платформах.

### Что делать прямо сейчас

```bat
:: 1. HTTP-сайты (rutor и подобные) — схема http:// обязательна,
::    без неё адрес считается HTTPS-ом
python host\pick_multi.py --url http://rutor.info/ --url https://rutor.info/ --apply -y

:: 2. если Instagram не подобрался вместе с ними — отдельно
python host\pick_multi.py --url https://www.instagram.com/ --limit 20 --apply -y
```

Если по Instagram ни один кандидат не сработал — значит блокировка по IP или по
TLS-отпечатку, и десинхронизация здесь бессильна в принципе. Тогда нужен
`transport=tunnel` (свой шлюз, `tunnel/README.md`) или обычный VPN; дальше
крутить аргументы ciadpi бесполезно.

## 11. «Работает только YouTube, остальное не открывается»

Это самая частая жалоба и самая обманчивая. **Открывающийся сайт не доказывает,
что обход работает.**

YouTube в России заблокирован не целиком: под блокировкой отдельные видео и
каналы, а сам `youtube.com` у большинства провайдеров открывается и без всякого
ciadpi. `google.com`, `ya.ru`, `example.com` не заблокированы вовсе. Значит
картина «YouTube открылся, а rutor.info и Instagram нет» совместима с тем, что
**обход не срабатывает нигде**, а YouTube просто и не был заблокирован.

Отсюда главное правило диагностики:

> Доказательство обхода — сайт, который БЕЗ прокси не открывается,
> а ЧЕРЕЗ прокси открылся. Всё остальное — не доказательство.

Перебирать режимы в попапе, пока «хоть что-то» не откроется, бесполезно: успех
на незаблокированном сайте выглядит как победа, а ничего не меняет.

### `host/verify.py` — что реально работает

Каждая цель бьётся дважды: напрямую (мимо ciadpi, с явным пустым
`ProxyHandler`, чтобы системный прокси не подмешался) и через SOCKS5-порт
ciadpi. Из двух результатов складывается один из четырёх диагнозов:

| Напрямую | Через прокси | Диагноз |
|---|---|---|
| ОК | ОК | `NOT_BLOCKED` — сайт не заблокирован, доказательством не является |
| НЕТ | ОК | `BYPASS_OK` — **обход работает**, вот это и есть успех |
| НЕТ | НЕТ | `BLOCKED_FAIL` — не работает; отдельная проба печатает, чем именно |
| ОК | НЕТ | `PROXY_BREAKS` — прокси портит то, что и так работало |

Плюс TLS-рукопожатие **с проверкой сертификата**, которое различает причины
блокировки. Это решает вопрос «есть ли вообще смысл подбирать аргументы»:

| `state` | Что произошло | Десинхронизация поможет? |
|---|---|---|
| `genuine` | сертификат настоящий, выдан для этого домена | блок не по TLS — смотреть контент |
| `mismatch` | сертификат валиден, но на ЧУЖОЙ домен (`verify_code 62`) | да, это подмена соединения |
| `untrusted` | цепочка не проверяется | да; хранилище Python отдельно проверяет `check_tls.py` |
| `reset` | TCP есть, рукопожатие оборвано (RST) | да, классический DPI-сброс |
| `noconnect` | TCP не устанавливается | **нет** — блок по IP/порту |

«Чем заблокировано» определяется не на глаз: `probe_verdict()` в `netutil.py`
уже отличает ответ настоящего сайта от провайдерской заглушки (`HTTP/1.0` или
5xx — так крупные сайты не отвечают), а `verify.py` добавляет к этому поведение
TCP и TLS.

Код возврата: `0` — обход доказан хотя бы на одной цели, `1` — не доказан,
`2` — прокси не поднят. На этом построен `fix.bat`.

### `fix.bat` / `fix.sh` — всё сразу, без попапа

```bat
fix.bat
```

1. `verify.py` по четырём целям (rutor.info, rutracker.org, instagram.com,
   youtube.com) в обеих схемах — показывает, что блокируется и чем;
2. если обход не доказан — `pick_multi.py` по тем же адресам с `--apply`
   (новый ключ `--fail-fast` прерывает подбор на первом неподобравшемся адресе:
   склеивать неполный набор бессмысленно, сначала надо понять причину);
3. `verify.py` ещё раз — уже на склеенной строке;
4. если что-то не открылось — печатает три возможные причины и что с каждой
   делать. Результат остаётся в `verify-result.json`, его можно прислать целиком.

Ничего закрывать и сохранять руками не нужно: `--apply` пишет `strategy=custom`
и `custom_args` в `config.json` и перезапускает ciadpi сам.

`fix.bat` в архиве хранится с CRLF и намеренно **не содержит ни меток, ни `goto`,
ни `call :label`** — вся логика во вложенных блоках `if ( ... )`. Причина:
`patch` нормализует концы строк в LF, а cmd.exe при LF-файле иногда криво
ищет метку, и скрипт начинает выходить не там. Блоки `if` от концов строк не
зависят, поэтому и через патч, и из архива `fix.bat` работает одинаково.
Плата — текст подсказки повторяется в файле дважды.

### Про «режим переключать — геморой»

Так и есть, через попап это неудобно. Три способа без попапа:

```bat
:: применить готовую строку и сразу проверить
python host\verify.py --apply-args "--split 1+h --disorder 3+h --auto=torst --timeout 3 --tlsrec 1+s" --quick

:: просто сменить режим (прокси перезапустится сам)
python host\ctl.py set strategy=universal
python host\ctl.py set strategy=custom "custom_args=--split 1+h --disorder 3+h --auto=torst --timeout 3 --tlsrec 1+s"

:: посмотреть, какая командная строка сейчас реально у ciadpi
python host\ctl.py args
```

`--apply-args` полезен именно тем, что применяет и проверяет за один раз: не
надо переключать, потом идти в браузер, потом гадать, применилось ли.

### Instagram, Facebook, Threads — отдельный случай

Для них в России блокировка по IP/ASN, а не по содержимому пакета. `verify.py`
помечает их строкой «ПОХОЖЕ НА БЛОКИРОВКУ ПО IP» и **исключает из команды
подбора**: рабочих аргументов ciadpi для них не существует в принципе, и
перебор всех 66 кандидатов ничего не даст. Нужен `transport=tunnel` (свой шлюз,
`tunnel/README.md`) или обычный VPN. Это не баг и не недоработка стратегии —
это другой класс блокировки.

### Что делать прямо сейчас

```bat
cd byedpi-win-1.2.0-fixed
fix.bat
```

Если в конце «ГОТОВО. Обход доказан» — всё, настройки сохранены и переживут
перезагрузку. Если «Открылось не всё» — прочитайте список причин выше и
пришлите `verify-result.json`: по нему видно, какой из трёх случаев у вас.

## 12. Сравнение с ByeByeDPI x tg для Android: почему там «одна кнопка»

Вопрос был прямой: у ребят на Android (и, как казалось, на ПК) всё работает из
коробки одной кнопкой, а тут надо подбирать. Разобрал их репозиторий
[EwenLoy/ByeByeDPI-x-tg](https://github.com/EwenLoy/ByeByeDPI-x-tg),
релиз `v1.0.1-build5`. Отвечаю по пунктам, потому что половина ответа — в вашу
пользу, а половина объясняет разницу честно.

### ПК-версии у них нет

В релизе `v1.0.1-build5` пять ассетов, и все пять — APK:

```
app-arm64-v8a-release.apk        3 994 271 B
app-armeabi-v7a-release.apk      3 669 293 B
app-universal-release.apk        5 534 783 B
app-x86-release.apk              2 849 402 B
app-x86_64-release.apk           2 852 413 B
```

`x86` и `x86_64` здесь — это **ABI Android** (эмуляторы и x86-планшеты), а не
Windows. В репозитории `build.gradle.kts`, `gradlew`, `app/src/main/java/...`,
бейдж `Android SDK 21-36`; ни одного артефакта для десктопа нет. Так что
сравнение «у них на ПК работает, у тебя нет» сравнивает Android-приложение
с расширением для Firefox.

### Их список стратегий — это наш список стратегий

В шапке `host/strategy_candidates.txt` источник указан с самого начала: их
`app/src/main/assets/proxytest_strategies.list`. Сверка построчно:

| | число |
|---|---|
| их стратегий в `proxytest_strategies.list` | 60 |
| наших кандидатов | 73 (было 72) |
| их строк, присутствующих у нас дословно или с исправлением | **60 из 60** |
| наших сверх их списка | 13 |

Четыре их строки не совпадали дословно ровно потому, что у них там же сидит баг
молча отбрасываемого хвоста флага, который мы чинили в разделе 1:

| их строка | что делает byedpi на самом деле | наша версия |
|---|---|---|
| `-s8+sh … -d6+sh … -r6+sh` | `parse_offset()` читает после `+` один символ из `{s,h,n}` и один из `{e,m,r,s}`, хвост игнорируется → `+sh` работает как `+s` | `-s8+h … -d6+h … -r6+h` |
| `-f1+nme -t6 …` | `+nme` работает как `+nm` | `-f1+nm -t6 …` |
| `-s4+sn -r9+s …` | `+sn` работает как `+s` | `-s4+s -r9+s …` |
| `-o1 -a1 -An -f1+nme -t6 -a1` | то же | `-o1 -a1 -An -f1+nm -t6 -a1` |

И семь их строк содержат `-S` (`--md5sig`), которого **нет в windows-сборке
ciadpi**: на Windows ciadpi вышел бы с «unknown option» и не поднял порт. У нас
их отбраковывает `load_candidates(plat="windows")` ещё до запуска — 73 → 66.
У них такой фильтрации нет, потому что им она не нужна: приложение только
Android.

Обратной стороной: их дефолта «из коробки» у нас не было. В
`utility/PreferencesUtils.kt`:

```kotlin
private const val DEFAULT_CMD_ARGS = "-o1 -a1 -r-5+se"
```

Аудит показывает, что он жив **и для HTTPS, и для обычного HTTP** (правило
`--oob 1` от позиции 0 не зависит ни от SNI, ни от заголовка Host) и не содержит
непереносимых опций. Добавлен в кандидаты первым.

### Что реально изменилось в нашем файле

`build_fixed4.py` пересортировал `strategy_candidates.txt` устойчивой
сортировкой по классу:

```
класс 0 — работают и на HTTPS, и на HTTP   38 строк   (идут первыми)
класс 1 — только один протокол             35 строк
класс 2 — мёртвы на обоих                    0 строк
```

Класс считается тем же `audit_offset_flags.py`, который эмулирует
`parse_offset()` → `gen_offset()` → `desync()`. Внутри класса исходный порядок
сохранён, так что файл остаётся диффируемым.

Эффект на Windows-сборке: **первые 36 пригодных кандидатов — все живы для
HTTP**, первый HTTP-мёртвый стоит на позиции 36 из 66. Раньше порядок был «как
в их исходнике», и `pick` (в отличие от `pick_multi`, который сортировал сам)
мог потратить `--stop-after 3` целиком на строки, привязанные только к SNI.
Для HTTP-трекера это и выглядело как «ничего не нашёл».

### А вот разница настоящая: транспорт

У них на Android:

```
весь трафик устройства -> Android VpnService (TUN)
                       -> hev-socks5-tunnel (submodule в .gitmodules)
                       -> byedpi SOCKS5 на 127.0.0.1:1080
```

Приложение объявляет себя VPN, система отдаёт ему **весь** трафик вместе с DNS,
плюс есть фильтр по приложениям (`appListType`, `apps` в `Configuration.kt`).
Отсюда «одна кнопка и всё»: не надо ни прописывать прокси в браузер, ни
отключать HTTP/3, ни думать про UDP — QUIC просто идёт через тот же TUN.

На Windows такой фокус требует **прав администратора и TUN-драйвера** (Wintun
или аналог). Этот проект намеренно без админских прав: единственное, что может
расширение Firefox, — `browser.proxy.settings` на SOCKS5. Отсюда три отличия,
которые вы и ощущаете:

| | Android + VpnService | Windows + расширение Firefox |
|---|---|---|
| охват | весь трафик устройства | только Firefox |
| DNS | через туннель автоматически | `proxyDNS: true` в расширении |
| QUIC / HTTP/3 | идёт через TUN | мимо SOCKS5 — надо выключать |
| права | запрос «разрешить VPN» | не нужны |

Это не «у них подход проще, а у нас сложнее» — это разные операционные системы
с разными правами. Ровно то же самое делает `transport=tunnel` в этом проекте,
но ему нужен ваш сервер.

### И главное: у них тоже есть подбор

В их README, раздел «Возможности», дословно:

> **Проверка стратегий:** приложение само перебирает варианты обхода и
> показывает рабочие.

Это `TestService.kt` (17 749 B) + `proxytest_*.sites` — тот же самый перебор,
что и наш `pick`/`pick_multi`, только спрятанный за кнопку. И строка в их
`strings.xml`:

```
test_good_cmds   Стратегии с наилучшим результатом, применяйте от большего к меньшему
```

То есть «универсальной стратегии не существует» — это не особенность нашей
сборки, а свойство DPI: у каждого провайдера своя. Разница только в том, что
у них дефолт подобран под **мобильные сети России** и в 9 случаях из 10
срабатывает без перебора, а у нас дефолт был другой. Теперь их дефолт стоит у
нас первым кандидатом.

Их `proxytest_*.sites` — готовые наборы целей (`general`, `social`, `youtube`,
`telegram`, `discord`, `cloudflare`, `googlevideo`, `türkiye`). Это ровно то,
что делает наш `verify.py`, только у них цели привязаны к кнопке теста, а у нас
набор можно задать через `--url`.

### Вывод

Перенимать у них оказалось нечего, кроме их же дефолта и порядка строк — и то
потому, что список стратегий у нас общий с самого начала. «Проще» у них
получается за счёт TUN-захвата всего трафика, который на Windows стоит
админских прав и драйвера, и за счёт подобранного под мобильные сети дефолта.
Подбор стратегий у них есть свой, он просто спрятан за кнопку.

## 13. Когда обход DPI бессилен: VPN на своём сервере

Разделы 9 и 11 упираются в один и тот же потолок: если `verify.py` показывает
`noconnect` или пишет «ПОХОЖЕ НА БЛОКИРОВКУ ПО IP», аргументов ciadpi для этого
сайта **не существует**. Фильтр режет адрес назначения, а не содержимое пакета,
и портить пакет бесполезно — его всё равно не пропустят. Для Instagram, Facebook
и Threads в России это основной сценарий.

Дальше есть два пути, и оба требуют свой сервер:

| | `transport=tunnel` (уже в проекте) | AmneziaWG на VPS |
|---|---|---|
| что нужно | сервер с доменом и TLS-сертификатом | VPS с root по SSH, от 1 ГБ RAM |
| права на ПК | не нужны | **нужны** (драйвер туннеля) |
| охват | только Firefox | вся система, все приложения |
| скорость | ниже: WSS поверх TLS, userspace | выше: WireGuard в ядре |
| настройка | своя, `tunnel/README.md` | одна команда, ~20 минут |

Второй путь разобран отдельно в **[`VPN.md`](VPN.md)** — там же три грабли,
из-за которых можно заплатить за VPS и не получить ничего:

1. **Блокировка по автономной системе хостера.** Фильтрация опирается на белый
   список примерно из 72 AS; Hetzner `AS24940`, OVH, DigitalOcean, AWS и
   Cloudflare в него не входят. Симптом: рукопожатие прошло, `latest handshake`
   обновился, пришли килобайты — и тишина. Junk-параметры `Jc`/`Jmin`/`Jmax` не
   спасают: они меняют сигнатуру пакета, а не адресата по AS.
2. **Мобильный интернет режет залп перед рукопожатием.** Ставить сразу с
   `--mobile`. Ловушка в том, что со стороны сервера связь выглядит живой:
   `endpoint` меняется, счётчик байт растёт, не обновляется только
   `latest handshake`.
3. **Поколение протокола.** Установка по умолчанию выдаёт AmneziaWG 3.1, а
   клиент без поддержки 3.1 профиль не примет и может не показать ошибки.
   Поколение работающего сервера меняется только переустановкой, поэтому решать
   надо до неё (`--protocol=2.0`).

Отдельно: рекомендация хостинга в их README содержит партнёрскую ссылку
(`aff.php?aff=392`), и цена €25/год за 2 vCPU с портом 10 Gbps выглядит
подозрительно дёшево. Брать надо месяц, а не год, и **сначала** проверить, что
IP доступен из России без VPN, а туннель держится с вашего провайдера.

Порядок действий остаётся прежним: сначала `verify.py` / `fix.bat`. Если там
`reset`, `mismatch` или заглушка `HTTP/1.0` — это лечится аргументами byedpi,
VPN не нужен и платить не за что. Если `noconnect` — смотрите `VPN.md`.

## 14. Когда не помогает вообще ничто из вышеперечисленного

Если `verify.py` говорит `BLOCKED_FAIL` на всех стратегиях, а VPN с обычным конфигом тоже не
поднимается — скорее всего, вы попали в **режим белых списков** (пропускают только разрешённые
сайты, всё остальное режут до установки соединения).

Это принципиально другая блокировка. byedpi маскирует содержимое пакетов уже установленного
соединения; в режиме белых списков соединение не устанавливается вовсе, поэтому **ни один набор
аргументов byedpi не поможет физически**. Это не дефект сборки.

Быстрый тест: откройте заведомо «белый» сайт (Госуслуги) и заведомо «чёрный». Если белый
работает, чёрный не работает **и при этом не работает даже через живой VPN** — это белые списки.

Что делать, какие подписки живые и как их проверить — см. **`WHITELIST.md`** и `WL-check.bat`.

## 15. Что исправлено после настоящего отчёта DNSFIX (2026-10-30)

Отчёт `dnsfix-report.txt`, присланный с живой машины, вскрыл четыре дефекта — три в
наших же инструментах и один в том, как мы считали «сайт открылся». Все четыре закрыты,
на каждый есть проверка в тестах.

### 15.1 `fix.bat` молча запускал python БЕЗ списка сайтов

`fix.bat` ставил переменную `URLS` внутри большого блока `if ... ( ... ) else ( ... )`
и там же её использовал как `%URLS%`. Это классическая ловушка cmd.exe: проценты
раскрываются **в момент разбора блока**, то есть до того, как внутри отработает `set`.
В python улетал пустой список `--url`, `verify.py` отвечал «не задан ни один --url»
и возвращал код 2, `pick_multi.py` — то же самое. Со стороны это выглядело как
«fix.bat ничего не делает».

Исправлено: включена `EnableDelayedExpansion`, все переменные читаются как `!URLS!`,
меток и `goto` в файле нет (при переносе `.bat` с CRLF на LF cmd.exe иногда
misparse'ит поиск метки — вся логика во вложенных `if`, они от концов строк не зависят).

### 15.2 Долгий подбор шёл в пустое окно

Подбор стратегии — это десятки кандидатов на сайт, от 3 до 20 минут. Перенаправлять
вывод в лог (`>> log.txt`) нельзя: человек смотрит в пустое окно и не понимает, идёт
процесс или завис — ровно так выглядел «молча закрывшийся» `DNSFIX.bat`. Не
перенаправлять — тоже нельзя: прислать нечего.

В Windows нет `tee`, а обёртка через PowerShell теряет код возврата и ломается на
кавычках. Поэтому tee написан сам: **`host/runlog.py`**. Он запускает дочерний процесс
с выводом в трубу и пишет строки одновременно в консоль и в файл, пробрасывает код
возврата, выставляет дочернему процессу `PYTHONIOENCODING=utf-8` (иначе лог на русской
Windows оказался бы в cp1251) и `PYTHONUNBUFFERED=1` (иначе вывод приходит кусками по
4-8 КБ вместо живого прогресса). Проверки — `test_dnsfix.py`, сценарий 26 (7 штук):
код возврата, видимость в окне, содержимое лога, `--append`, ошибка без команды.

### 15.3 «Сайт открылся» считалось по HTTP, а браузер ходит по HTTPS

Раздел 8 отчёта рапортовал «сайт открылся: 4», и это было неправдой: все четыре
(`rutor.info`, `rutor.is`, `rutracker.org`, `www.facebook.com`) отвечали **только по
HTTP** — 302 на 80 порту, — а HTTPS рвали по SNI. Firefox идёт по HTTPS, значит не
открывалось ничего. Зелёные цифры в отчёте при неработающем браузере — худший из
возможных результатов: человек перестаёт доверять инструменту.

Исправлено: подсчёт вынесен в чистую функцию `classify_rechecks()`, HTTP-успех
считается отдельно (`http_only`) и в вердикте приравнивается к незакрытому сайту, а
раздел 8 печатает дословно:

```
      сайт открылся по HTTPS:      0
      открылся ТОЛЬКО по HTTP:     4
      не открылся вовсе:           2 (из них рвут на TLS: 0, не поднимается TCP: 2)

   ПРО «ТОЛЬКО ПО HTTP» — ЧИТАТЬ ОБЯЗАТЕЛЬНО.
   Ответ 200/302 на 80 порту доказывает, что адрес теперь настоящий и
   сервер жив. Но браузер открывает сайты по HTTPS...
```

Отдельно разделены два разных «не открылось»: сброс на TLS (блокировка по SNI —
лечится десинком) и таймаут на TCP (блокировка **по адресу** — не лечится аргументами
ciadpi в принципе, нужен туннель). В отчёте 2026-10-30 к первому не относился никто,
ко второму — `new-rutor.org` и `www.instagram.com`.

Проверки — `test_dnsfix.py`, сценарии 20-22 (14 штук), причём сценарий 20 построен
**на данных настоящего отчёта**, а не на выдуманных.

### 15.4 Группы `--hosts` не покрывали CDN и видеопоток

Группа, в которой стоит один `www.facebook.com`, покрывает только HTML: картинки и
скрипты едут с `fbcdn.net`, видео YouTube — с `googlevideo.com`. Десинк применяется
только к соединениям из группы, поэтому «недокрытая» страница выглядит не как ошибка,
а как «открылось наполовину» или «плеер крутится и не стартует».

В `pick_multi.py` добавлены таблица `COMPANIONS` и функция `expand_hosts()`: к домену-
победителю дописываются его спутники. Списки взяты из гайда Flowseal discussion #8778
(Twitter/X, Facebook, Instagram) и дополнены `googlevideo.com`, `ytimg.com`, `ggpht.com`
для YouTube и `discordapp.net`, `discord.media` для Discord. Соответствие работает как
`host_cmp()` из `mpool.c` (сравнение с конца строки, граница — точка), поэтому записи
`fbcdn.net` достаточно для `scontent.xx.fbcdn.net`; `notfacebook.com` спутников не
получает — это проверено отдельно. Проверки — `test_hosts_groups.py`, 27 штук, включая
лимит командной строки Windows (8191 символ) на группе из восьми сервисов.

### 15.5 `fix.bat` больше не останавливается на первом же непробитом сайте

Флаг `--fail-fast` обрывал перебор на первом сайте, который не пробился, и до остальных
дело не доходило. При этом склеивались и применялись всё равно только победители, то
есть пользы от обрыва не было никакой. Флаг убран; сайты с блокировкой по адресу теперь
исключаются заранее — списком из `dnsfix-pins.json` (см. `--emit-fix-urls` в `DNSFIX.py`).

### 15.6 Что стало с `DNSFIX.bat`

Он больше не перезапускает самого себя через UAC. Прежняя схема ломалась молча:
повышенное окно живёт своей жизнью и закрывается мгновенно, а `python.exe`, поставленный
из Microsoft Store, в повышенном контексте часто не находится вовсе (алиас `WindowsApps`).
Теперь права нужны ровно на одно действие — перенести подготовленный файл hosts
(`DNSFIX-apply-hosts.ps1`), всё остальное считается в обычном окне: `[1/3]` подготовка
и разделы 1-6, `[2/3]` перенос, `[3/3]` проверка и разделы 7-8 **в тот же файл**.
Окно не закрывается молча ни при каком исходе: в конце `pause`, весь вывод — в
`dnsfix-log.txt`, а если отчёт не создался, батник печатает последние 30 строк лога.

Проверено сквозным прогоном на стенде с подделанной подменой и отобранными правами
администратора: 29 из 29 (подготовка → перенос → проверка → откат → ветка «UAC
отклонён»), плюс 80 проверок чистой логики в `test_dnsfix.py` и 27 в
`test_hosts_groups.py`.
