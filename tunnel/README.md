# tunnel — трафик внутри настоящего HTTPS-соединения

Альтернативный транспорт для byedpi-firefox. Вместо того чтобы «портить» TLS-рукопожатие
(чем занимается ciadpi), туннель прячет весь трафик **внутри обычного WSS-соединения
с вашим сайтом-шлюзом**. Для провайдера это выглядит как то, что вы открыли HTTPS-сайт:
порт 443, настоящий сертификат, настоящий TLS 1.3, внутри — нормальные WebSocket-кадры.

```
 Firefox ──SOCKS5──> 127.0.0.1:1080
                          │
                    tunnel/client.py         (у вас на ПК)
                          │  одно WSS-соединение, внутри — много потоков
                          ▼  wss://ваш-домен:443/live
                    tunnel/relay.py          (ваш сервер)
                          │  обычный TCP наружу
                          ▼
                     настоящие сайты
```

Контракт с расширением не меняется: локальный SOCKS5 на `127.0.0.1:1080`, DNS разрешается
на шлюзе. Поэтому расширение, менеджер и native-хост разницы между `ciadpi` и `tunnel`
не замечают — переключение делается одной настройкой `transport`.

---

## Главное, что нужно понять заранее

**Туннелю нужен ваш сервер.** В отличие от ciadpi, который работает сам по себе,
этот транспорт — пара «клиент + шлюз», и шлюз надо где-то держать: VPS за ~200 ₽/мес
или домашняя машина с белым IP и доменом. Без шлюза туннель не заработает вообще.

Если своего сервера нет — используйте `transport: "ciadpi"`, он по-прежнему основной.

---

## 1. Сервер (шлюз)

Нужны: домен, направленный на сервер, и TLS-сертификат на этот домен.

```bash
# сертификат (Let's Encrypt)
certbot certonly --standalone -d notes.example.com

# сгенерировать общий ключ
python3 -m tunnel.relay --gen-secret

# запустить шлюз
sudo python3 -m tunnel.relay \
    --cert /etc/letsencrypt/live/notes.example.com/fullchain.pem \
    --key  /etc/letsencrypt/live/notes.example.com/privkey.pem \
    --port 443 \
    --secret 'КЛЮЧ_ИЗ_ПРЕДЫДУЩЕЙ_КОМАНДЫ'
```

Порт 443 требует root (или `setcap 'cap_net_bind_service=+ep'` на обёртке).

Шлюз ведёт себя как обычный сайт:

| Запрос | Ответ |
|---|---|
| `GET /` обычным браузером | HTML-страница-заглушка (200) |
| `GET /robots.txt` | robots.txt |
| `GET /live` без `Upgrade: websocket` | 404, как у любого сайта |
| `GET /live` с WebSocket-рукопожатием, но без верного ключа | 403 |
| `GET /live` с рукопожатием **и** верным ключом | 101 Switching Protocols → туннель |
| любой другой путь | 404 |

То есть снаружи нельзя отличить шлюз от сайта, а без ключа он не отдаёт ничего —
открытым прокси он не становится даже если адрес утечёт.

Полезные флаги:

- `--ws-path /live` — путь эндпоинта (меняйте, чтобы не угадывали);
- `--site-file my.html` — своя страница-заглушка вместо встроенной;
- `--allow example.com,example.org` — разрешить выход только на эти домены;
- `--deny ...` — наоборот, запретить;
- `--quiet` — не писать про каждое подключение.

За reverse-proxy (nginx/caddy) обязательно пробрасывайте `Upgrade` и `Connection`,
иначе рукопожатие не пройдёт и клиент сообщит «сервер не поднял WebSocket».

## 2. Клиент

В `config.json` (или через webui/ctl):

```json
{
  "transport": "tunnel",
  "host": "127.0.0.1",
  "port": 1080,
  "tunnel": {
    "relay": "wss://notes.example.com/live",
    "secret": "КЛЮЧ_С_СЕРВЕРА",
    "ca": "",
    "insecure": false,
    "impersonate": "chrome",
    "engine": "auto"
  }
}
```

- `ca` — путь к PEM-файлу, если сертификат выдан вашим собственным CA;
- `insecure` — не проверять сертификат. **Только для локальных тестов**: с этим
  флагом трафик можно перехватить, подменив шлюз;
- `engine` — чем держать WSS-соединение:
  - `auto` (по умолчанию) — `curl_cffi`, если он установлен, иначе стандартная библиотека;
  - `curl` — только `curl_cffi`;
  - `stdlib` — только стандартная библиотека, работает везде без зависимостей.
- `impersonate` — отпечаток браузера для `curl_cffi` (`chrome`, `chrome131`, `safari`, `edge`…).

**Про отпечаток.** Запасной транспорт на стандартной библиотеке поднимает TLS руками
питона, и его JA3/JA4 — питоновские: технически трафик зашифрован и работает, но
автоматический анализ может отличить его от браузера. `curl_cffi` повторяет рукопожатие
и HTTP/2 настоящего Chrome, поэтому для постоянного использования ставьте его:

```bash
pip install curl_cffi
```

Проверить, какой движок подхватился: `python3 host/ctl.py status` (поле `binary.engine`).

Отдельно, без менеджера, клиент запускается так:

```bash
python3 -m tunnel.client --relay wss://notes.example.com/live --port 1080
# ключ лучше передавать через окружение, а не в командной строке:
TUNNEL_SECRET='КЛЮЧ' python3 -m tunnel.client --relay wss://notes.example.com/live
```

Ключ намеренно **не** кладётся в argv: командную строку процесса видит любой локальный
пользователь через `ps` и `/proc/<pid>/cmdline`. Хост передаёт его через `TUNNEL_SECRET`.

## 3. Локальная проверка без интернета

```bash
openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem \
    -days 2 -subj /CN=localhost -addext subjectAltName=DNS:localhost,IP:127.0.0.1

python3 -m tunnel.relay  --cert cert.pem --key key.pem --port 8443 --secret S
python3 -m tunnel.client --relay wss://127.0.0.1:8443/live --secret S \
                         --port 1080 --ca cert.pem
```

Дальше в Firefox: SOCKS5, `127.0.0.1:1080`, «Proxy DNS when using SOCKS v5».

## Протокол

Внутри одного WSS-соединения мультиплексируется до 65535 TCP-потоков. Каждый кадр —
двоичный WebSocket-кадр с заголовком из 3 байт:

```
 0        1        2        3 ...
+--------+--------+--------+----------------+
|  тип   |  sid (uint16)  |   полезные     |
+--------+--------+--------+----------------+
```

| Тип | Значение | Смысл |
|---|---|---|
| `OPEN`  | 0x01 | клиент просит соединиться; в payload `host\0порт(2 байта, BE)` |
| `DATA`  | 0x02 | байты потока (до 16 КБ на кадр) |
| `CLOSE` | 0x03 | поток закрыт |
| `OK`    | 0x04 | шлюз соединился, можно слать данные |
| `ERR`   | 0x05 | шлюз не смог соединиться; в payload причина |
| `PING`  | 0x06 | проверка живости (раз в 20–25 с простоя) |
| `PONG`  | 0x07 | ответ на PING |

Детали, которые легко сломать и которые поэтому зафиксированы тестами:

- в `OPEN` целевой адрес отделяется от порта **первым** нулевым байтом
  (`partition`, а не `rpartition`) — иначе порты меньше 256 читаются неверно,
  потому что старший байт порта сам равен `0x00`;
- хост в `OPEN` — UTF-8, а в SOCKS5-запросе домен приходит байтами и декодируется
  как ASCII с заменой: кодек `idna` не принимает `errors=`, и на «кривом» имени
  он бросает `UnicodeError` вместо того, чтобы просто передать имя шлюзу;
- сравнение ключа идёт побайтово через `secrets.compare_digest` по
  `encode("utf-8", "replace")`: сравнение строк падает на не-ASCII ключе,
  а побайтовое заодно не зависит от длины;
- сокет закрывается через `shutdown(SHUT_RDWR)` **и только потом** `close()`.
  Один `close()` не отправляет FIN, если в другом потоке на этом же сокете висит
  блокирующий `recv()`, — вторая сторона ждёт EOF вечно. Это выглядело как
  «данные дошли, а соединение не закрывается».

## Ограничения

- **UDP и HTTP/3 не туннелируются.** Только TCP. Поэтому расширение отключает HTTP/3
  через `user.js` (`network.http.http3.enable=false`): иначе браузер полезет в QUIC
  мимо прокси. `BIND` и `UDP ASSOCIATE` в SOCKS5 отвечают кодом 0x07.
- Все потоки идут через одно WSS-соединение: порядок байт внутри потока сохраняется,
  но один медленный поток не блокирует другие (у каждого своя очередь).
- Шлюз видит, куда вы подключаетесь (он и делает DNS). Доверие к шлюзу = доверие
  к VPN-провайдеру.

## Безопасность

- без `--secret` шлюз отвечает 403 на всё — стать открытым прокси он не может;
- ключ сравнивается через `compare_digest` (без тайминг-утечки);
- TLS только 1.2+, набор шифров ECDHE+AESGCM/CHACHA20, без aNULL/MD5/DSS;
- `--insecure` у клиента отключает проверку сертификата — только для тестов;
- ключ не попадает ни в argv, ни в лог, ни в `status()`.

## Тесты

```bash
python3 tests/test_30_tunnel.py                 # 50 тестов, стандартная библиотека
/tmp/tunnel-venv/bin/python tests/test_30_tunnel.py   # + транспорт curl_cffi
python3 tests/run_all.py                        # весь проект
```

Всё проверяется на loopback, интернет не нужен: поднимается настоящий TLS-шлюз,
настоящий origin-сайт, и сквозь них гоняются запросы — включая многокадровую
передачу, десятки одновременных потоков, отказ при неверном ключе, поведение
шлюза как обычного сайта и интеграцию с хостом (`transport: tunnel` → подпроцесс
→ SOCKS5 → ответ), в том числе автоперезапуск после `kill -9`.

Часть тестов пропускается, если окружение не подходит: без `curl_cffi` не проверяется
Chrome-транспорт, с ним — подсказка об установке. Два прогона (системным питоном
и питоном из venv) вместе покрывают оба случая.
