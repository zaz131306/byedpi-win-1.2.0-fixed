# byedpi-firefox

Управление локальным SOCKS5-прокси из Firefox: запуск/остановка, автоматическая прописка
прокси в настройки браузера. Работает на Linux, macOS и Windows, без прав администратора.

Трафик Firefox направляется через `127.0.0.1:1080` (SOCKS v5, DNS через прокси).
Контракт с расширением один и тот же, а вот **что стоит за этим портом** — выбирается
настройкой `transport`:

| `transport` | Что делает | Что нужно |
|---|---|---|
| `ciadpi` (по умолчанию) | локальный обход DPI — «портит» TLS-рукопожатие так, чтобы фильтр не узнал заблокированный сайт. Это **[byedpi](https://github.com/hufrea/byedpi)** | только бинарник `ciadpi` (лежит в `bin/`) |
| `tunnel` | прячет весь трафик **внутри обычного WSS-соединения с вашим сайтом-шлюзом**: снаружи это просто HTTPS на 443 | свой сервер с доменом и сертификатом, см. [tunnel/README.md](tunnel/README.md) |

Переключение не требует переустановки расширения — меняется только `config.json`.

## Два варианта расширения

Ставится **что-то одно** — у обоих одинаковый ID (`byedpi-control@byedpi.local`),
поэтому уже зарегистрированный native-хост переустанавливать не нужно.

| | `simple/` | `addon/` |
|---|---|---|
| Для кого | «поставил и забыл» | когда нужен контроль |
| Интерфейс | один переключатель вкл/выкл | стратегии, порт, свои аргументы ciadpi, журнал, web-панель |
| Автозапуск при старте браузера | да, по умолчанию | настраивается |
| Самолечение при падении прокси | да (3 попытки, дальше раз в минуту) | перезапуск по флагу |
| Страница настроек | нет | `help.html` |
| Версия | 1.0.1 | 1.2.0 |

Оба варианта **не хранят настройки в себе**: единственный источник правды —
`config.json` локального менеджера. Правится он полной версией или
`python3 host/ctl.py set ключ=значение`.

## Архитектура

```
Firefox (simple/ или addon/)
   │  browser.runtime.connectNative()          — Native Messaging, stdio
   ▼
host/native_host.py   Bridge + live-контроль   — мост, отвечает на host_info без менеджера
   │  локальный control-сокет
   ▼
host/manager.py       Manager                  — один на систему, держит статус и конфиг
   │
   ├─ host/proxy_core.py   — поднимает/гасит процесс SOCKS5 и собирает ему argv
   │     ├─ ByedpiProxy    — transport=ciadpi: бинарник ciadpi + аргументы стратегии
   │     └─ TunnelProxy    — transport=tunnel: `python -m tunnel.client`
   │                              └─ WSS на 443 → tunnel/relay.py (ваш сервер) → сайты
   ├─ host/webui.py        — панель на 127.0.0.1:8787 (токен в URL)
   └─ host/ctl.py          — CLI: status / start / stop / selftest / logs / set / webui
```

`make_proxy(cfg)` выбирает класс по `cfg["transport"]`. Дальше менеджер, native-хост
и расширение работают с любым из них одинаково: и тот и другой — локальный SOCKS5
на `host:port`.

Менеджер живёт отдельным процессом, поэтому «засыпание» event-page расширения или
закрытие попапа интернет не рвёт: при возврате расширение переподключается и
перечитывает статус.

## Транспорт `tunnel`

Отдельный пакет [`tunnel/`](tunnel/README.md): сайт-шлюз (`relay.py`), клиент
(`client.py`) и протокол мультиплексирования (`protocol.py`). Клиент держит **одно**
WSS-соединение и прогоняет внутри него до 65535 TCP-потоков, поэтому провайдер видит
обычный HTTPS-трафик на 443, а не SOCKS-прокси и не испорченное TLS-рукопожатие.

Шлюз при этом ведёт себя как настоящий сайт: на `/` отдаёт HTML-страницу, на мусор —
404, а без верного ключа не переключается в WebSocket вообще (403), то есть открытым
прокси не становится.

```bash
python3 host/ctl.py set transport=tunnel \
                        tunnel.relay=wss://ваш-домен/live \
                        tunnel.secret=КЛЮЧ_С_СЕРВЕРА
python3 host/ctl.py args      # показать, что получится (ключ не печатается)
```

Движок WSS: `curl_cffi`, если он установлен (`pip install curl_cffi`) — тогда
TLS-рукопожатие повторяет настоящий Chrome; иначе стандартная библиотека Python,
которая работает везде без зависимостей. Настройка `tunnel.engine`: `auto` · `curl` · `stdlib`.

**Важно:** туннелю нужен свой сервер. Если его нет — оставайтесь на `ciadpi`.

## Стратегии обхода DPI

Пресеты в `host/strategies.py`, аргументы взяты из документации byedpi:

`recommended` · `universal` · `http` · `fake` · `fake-ttl` · `disorder` · `oob` ·
`tlsrec` · `aggressive` · `ladder` · `plain` (чистый SOCKS5 для диагностики) ·
`custom` (свои аргументы)

Прежде чем подбирать стратегию вручную, проверьте сам набор аргументов — он может
выглядеть рабочим и при этом не фрагментировать HTTP вовсе:

```bash
python host\audit_offset_flags.py .      # Windows
python3 host/audit_offset_flags.py .     # Linux / macOS
```

Скрипт эмулирует `parse_offset()` / `gen_offset()` / `desync()` и разбиение на
группы по `--auto` из byedpi v0.17.3 и печатает для каждого пресета и кандидата,
применится ли он к HTTPS- и к HTTP-запросу.

Подробный разбор найденных дефектов — в [`FIX.md`](FIX.md).

`recommended` — базовая десинхронизация плюс `--auto=torst`: ciadpi сам переключается
на `tlsrec` при признаках блокировки (сброс соединения или таймаут).

### Если HTTPS-сайты открываются, а обычные HTTP — нет

Дело во флаге позиции. В byedpi смещение задаётся как `offset+flags`, где

| Флаг | К чему привязано правило |
|---|---|
| `+s` | к SNI — **только TLS**: на HTTP-запросе `gen_offset()` возвращает −1 |
| `+h` | к имени хоста — **и TLS (позиция SNI), и HTTP (заголовок `Host`)** |
| `+n` | без привязки, абсолютное смещение |
| `+e` `+m` `+r` `+s` | второй символ после `+`: конец / середина / случайно / начало |

> **Важно.** Комбинации `+sh` в byedpi **не существует**. `parse_offset()`
> (main.c, v0.17.3) читает после `+` ровно один символ из `{s,h,n}` и один
> дополнительный из `{e,m,r,s}`, остаток строки **молча отбрасывается** —
> ошибки не будет. То есть `--split 1+sh` работает в точности как
> `--split 1+s`, а на обычном HTTP не работает вовсе. Универсальный флаг — `+h`.

Правило с `+s` на сайте без HTTPS не срабатывает: SNI физически отсутствует,
`gen_offset()` возвращает −1, `desync()` печатает `split cancel` и делает `break` —
запрос уходит **нефрагментированным**, а заодно отменяются все правила группы,
стоящие после него — при этом прокси выглядит полностью рабочим: SOCKS5
отвечает, HTTPS-сайты открываются, а трекеры, зеркала и форумы нет.

Для таких сайтов берите `universal` (правила `+h`, покрывают оба протокола) или
`http` (только `+h` плюс `--mod-http h`, перемешивающий регистр в `Host`):

```bash
python3 host/ctl.py set strategy=universal
python3 host/ctl.py set strategy=http
```

Проверить конкретный сайт (домен без схемы проверяется по HTTP и HTTPS отдельно —
именно это и показывает, в протоколе ли дело):

```bash
python3 host/ctl.py doctor --url rutor.info,example.org
```

## Автоподбор стратегии: `pick`

Если ни один пресет не пробивает (провайдер режет соединение RST-инъекцией),
не угадывайте вручную — пусть подберёт само. `host/strategy_candidates.txt`
содержит **60 проверенных наборов аргументов** из проекта
[ByeByeDPI-x-tg](https://github.com/EwenLoy/ByeByeDPI-x-tg) (GPL-3.0-or-later).
`pick` ставит их в ciadpi по очереди и пробует открыть ваш сайт:

```bash
# Windows
python host\ctl.py pick --url https://rutracker.org/ --apply -y

# Linux / macOS
python3 host/ctl.py pick --url https://rutracker.org/ --apply -y
```

Как это устроено:

| Что | Как |
|---|---|
| Отбор кандидатов | аргументы сверяются со **строками самого бинарника**: опции, которых он не знает (`--md5sig` в сборке Windows и т.п.), отбрасываются заранее — иначе ciadpi выходит с «unknown option» и не поднимает порт |
| `{sni}` | подставляется доменом из `--url`: `--fake-sni` должен нести настоящее имя сайта |
| Критерий успеха | сквозь прокси пришёл **любой HTTP-ответ**. Обрыв соединения и таймаут — провал. Код ответа не важен: 403 от Cloudflare означает, что DPI уже пройден |
| `--apply` | победитель сохраняется как `strategy=custom` + `custom_args`. **Без** `--apply` исходные настройки возвращаются на место — можно просто посмотреть |

> **`pick` подбирает под один сайт.** Победитель по YouTube не заставит работать
> rutor.info и Instagram — это глобальная строка для всего трафика. Чтобы у
> каждого домена была своя стратегия, смотрите `pick_multi.py` ниже.

Прочие ключи (значения по умолчанию):

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `--url` | `https://rutracker.org/` | сайт-проба |
| `--stop-after` | `3` | сколько успешных стратегий достаточно, чтобы остановиться |
| `--limit` | `0` | не больше N проб (`0` = перебрать всех кандидатов) |
| `--timeout` | `12` | секунд на одну пробу |

Во время подбора прокси перезапускается, браузер в эти минуты не работает.

Если `pick` не нашёл ничего — десинхронизацией ваш DPI не обходится. Тогда остаётся
туннель через свой сервер: `transport=tunnel`, см. `tunnel/README.md`.

### Автоподбор под несколько сайтов сразу (`pick_multi.py`)

`pick` подбирает стратегию **под один сайт** и сохраняет её глобально — для всего
трафика. Если подобрать по YouTube, rutor.info и Instagram от этого работать не
станут: у них разные блокировки, и одна строка аргументов не может подойти всем.

`pick_multi.py` решает это: он гоняет автоподбор отдельно по каждому адресу, а
потом склеивает победителей в одну строку с **доменными группами byedpi**:

```
--hosts :rutor.info --proto h -s1+h -d3+h -Mh -a1 --auto=none --hosts :rutor.info --proto t -s1+s -d3+s -At,r,s -r1+s --auto=none --hosts ":www.instagram.com youtube.com" --proto t -o1 -d1 -a1 --auto=none --split 1+h --disorder 3+h --auto=torst --timeout 3 --tlsrec 1+s
```

Каждая группа включается только для своих доменов (`--hosts`) и своего протокола
(`--proto h` — обычный HTTP, `--proto t` — HTTPS); `--auto=none` начинает новую
группу. Победа на YouTube больше не мешает rutor.info — каждый домен идёт своей
стратегией.

```bat
python host\pick_multi.py ^
    --url http://rutor.info/ ^
    --url https://rutor.info/ ^
    --url https://www.instagram.com/ ^
    --url https://www.youtube.com/ ^
    --apply -y
```

Схему указывайте явно: адрес без `http://`/`https://` считается HTTPS-ом. Один и
тот же домен по HTTP и по HTTPS — это две разные группы с разными параметрами,
поэтому для HTTP-трекера `http://` обязателен. `--apply` записывает результат в
`strategy=custom` и перезапускает прокси; без него строка только печатается.
Остальные ключи: `--limit N` (кандидатов на адрес), `--stop-after N` (достаточно
N побед), `--timeout`, `--dump`.

Два правила, без которых группа работать не будет:

* **последняя группа — без `--hosts`**. Это «всё остальное». Без неё byedpi
  просто обрывает соединения с доменами, которых нет ни в одной группе
  (`drop connection` в логе). `pick_multi.py` добавляет её сам — не удаляйте.
* **`--hosts` действует только до следующего `--auto`**. Если внутри победителя
  есть свой `--auto ...` (подгруппы), `--hosts` надо повторить перед каждой из
  них, иначе часть подгрупп останется «без домена» и будет ловить весь трафик.
  `pick_multi.py` делает это автоматически.

Домены пишутся строчными, без схем и путей; поддомены совпадают сами
(`--hosts :rutor.info` покроет и `www.rutor.info`). Несколько доменов в одной
группе — через пробел внутри кавычек.

Если по какому-то адресу победителя нет вовсе (часто Instagram) — это не баг
подбора: там блок по IP или по TLS-отпечатку, и десинхронизация его не берёт.
Для таких доменов остаётся туннель: `transport=tunnel` (см. `tunnel/README.md`)
или VPN на своём сервере — что выбрать и на какие грабли не наступать,
разобрано в [`VPN.md`](VPN.md).

> Откуда взялся список кандидатов и чем этот проект отличается от
> Android-приложения ByeByeDPI x tg, где «одна кнопка и всё работает» —
> разобрано в [`FIX.md`](FIX.md), раздел 12. Коротко: список стратегий у нас
> общий (их `proxytest_strategies.list`), а разница — в транспорте: там
> Android `VpnService` забирает весь трафик устройства, здесь расширение
> Firefox работает без прав администратора и видит только браузер. Подбор
> стратегий у них тоже есть («Проверка стратегий» в их README), просто спрятан
> за кнопку.

## «Открывается только YouTube» — как проверить по-настоящему

Открывающийся сайт **не доказывает**, что обход работает. YouTube в России
заблокирован не целиком (блокируют отдельные видео), `google.com` и `ya.ru` не
заблокированы вовсе. Если открывается только это — возможно, ciadpi просто
пересылает байты, а обход не срабатывает нигде. Доказательство обхода ровно
одно: сайт, который **без прокси не открывается**, а через прокси открылся.

```bat
:: Windows — всё сразу: проверка, подбор, перепроверка
fix.bat

:: только диагностика, ничего не меняет
python host\verify.py
```

`fix.bat` занимает от 3 до 20 минут и всё это время печатает, какой кандидат
пробуется и чем кончилось; копия вывода пишется в `fix-log.txt` — её и присылай,
если что-то пошло не так. Если рядом лежит `dnsfix-pins.json` (его создаёт
`DNSFIX.bat`), список сайтов берётся оттуда, а сайты с блокировкой **по адресу**
пропускаются: для них не существует рабочих аргументов ciadpi, и перебор
кандидатов на них — просто потерянные полчаса.

`verify.py` бьёт каждую цель дважды — напрямую (мимо ciadpi) и через SOCKS5-порт
— и складывает из двух результатов диагноз:

| Напрямую | Через прокси | Диагноз |
|---|---|---|
| открывается | открывается | сайт не заблокирован — **доказательством не является** |
| не открывается | открывается | **ОБХОД РАБОТАЕТ** — вот это и есть успех |
| не открывается | не открывается | не работает; ниже печатается, чем именно заблокировано |
| открывается | не открывается | прокси **портит** то, что и так работало |

Плюс TLS-проба с проверкой сертификата, которая различает настоящие причины
блокировки:

| `state` | Что это | Лечится аргументами ciadpi? |
|---|---|---|
| `genuine` | сертификат настоящий, сайт отвечает | да, если контент всё же не проходит |
| `mismatch` | сертификат выдан на чужой домен — соединение подменили | да (десинхронизация) |
| `untrusted` | цепочка не проверяется — подмена своим CA либо неполное хранилище Python | да; хранилище проверяет `check_tls.py` |
| `reset` | TCP есть, рукопожатие оборвали (RST) | да, это классический DPI |
| `noconnect` | TCP не устанавливается | **нет** — блок по IP, нужен `transport=tunnel` |

Ключи: `--url` (свои адреса, можно несколько), `--quick` (только заведомо
заблокированные), `--both-schemes` (проверить каждый адрес и по `http://`, и по
`https://`), `--json файл`, `--no-tls`, `--apply-args "СТРОКА"`.

`--apply-args` отдельно полезен, когда бесит переключать режим руками через
попап: он применяет строку как `strategy=custom`, перезапускает ciadpi, ждёт
порта и сразу проверяет — всё одной командой, ничего закрывать и сохранять не
нужно.

```bat
python host\verify.py --apply-args "--split 1+h --disorder 3+h --auto=torst --timeout 3 --tlsrec 1+s" --quick
```

Если по какому-то сайту победителя нет вовсе и `verify.py` пишет «ПОХОЖЕ НА
БЛОКИРОВКУ ПО IP» (обычно Instagram, Facebook, Threads) — рабочих аргументов
ciadpi для него **не существует**: фильтр режет адрес назначения, а не
содержимое пакета. Дальше помогает только `transport=tunnel` (свой шлюз) или VPN.

## «Не помогает ничто» — режим белых списков

Если `host\verify.py` пишет `BLOCKED_FAIL` на всех стратегиях, а обычный VPN-конфиг тоже
не поднимается, — скорее всего вы в **режиме белых списков**: фильтр пропускает только
разрешённые сайты и IP, всё остальное режет **до** установки соединения.

byedpi маскирует содержимое пакетов уже установленного соединения. Когда соединение не
устанавливается вовсе, маскировать нечего — поэтому в этом режиме **не существует** рабочих
аргументов ciadpi. Это не дефект сборки, а физика.

Быстрый тест: откройте заведомо «белый» сайт (Госуслуги) и заведомо «чёрный». Если белый
работает, чёрный не работает **и при этом чёрный не работает даже через заведомо живой VPN** —
это белые списки.

Дальше нужен канал, который сам проходит через белый список: VLESS-REALITY с SNI белого
российского домена, выход через подсети VK/Яндекса/CDNVIDEO, xhttp через CDN, DNS-туннель как
крайняя мера. Разбор пяти рабочих источников, живые ссылки, механизмы и риски — в
**`WHITELIST.md`**. Проверить, какие зеркала подписок отвечают прямо сейчас:

```bat
WL-check.bat
```

Скрипт только читает URL и считает живые профили; ничего не устанавливает и не меняет.
Результат — в `wl-check-result.txt`. Python не нужен: `.bat` найдёт его сам или предложит
скачать портативный в `%TEMP%`.

## Не работает сайт: `DIAG.bat`

Одна команда, и больше ничего делать не нужно:

```bat
DIAG.bat
```

Скрипт сам прочитает конфиг byedpi, проверит процессы и порт, посмотрит DNS,
откроет каждый сайт **напрямую** и **через прокси**, сравнит и напишет вывод
**словами**. В конце сам откроет отчёт в Блокноте.

Результат — файл `diag-report.txt`. Его нужно переслать целиком; интерпретировать
ничего не требуется, разделы 7 и 10 уже содержат выводы и конкретные команды.

Занимает 1–3 минуты. Проверяются 10 сайтов × 2 способа = 20 замеров, в набор
уже входят `rutor.info` (http и https), зеркала `rutor.is` / `new-rutor.org`,
`flow.google.com`, `google.com`, `youtube.com`, `rutracker.org`, `instagram.com`
и контрольный `gosuslugi.ru`.

Добавить свой адрес: `python DIAG.py --url https://адрес/`

### Почему http:// и https:// проверяются отдельно

Это **разные** стратегии обхода. Картина «HTTPS открывается, а HTTP нет»
(и наоборот) встречается постоянно и лечится по-разному: в byedpi для этого
есть `--hosts` и `--proto h` / `--proto t`. Первая версия диагностики смотрела
«открылся ли хоть один вариант» и на таком случае выдавала ложное
«не заблокировано» — исправлено, регрессию ловит `test_diag_verdict.py`
(12 сценариев, покрывают все 9 вердиктов).

Подробности — в `DIAG.md`.

## Вся сеть одним файлом: `NETSTAT.bat`

```bat
NETSTAT.bat
```

`DIAG.bat` отвечает на вопрос «открывается ли сайт». `NETSTAT.bat` — на вопрос
«что вообще происходит в сети»: процессы, порт SOCKS5 и кто к нему подключён,
все активные TCP-соединения, маршруты и шлюз, адреса интерфейсов, прописанный
в системе DNS, **сравнение резолверов** (системный против `77.88.8.8` против
`195.208.4.1`), проба подозрительного IP по HTTP и HTTPS, настройки Firefox
(`trr.mode`, `socks_remote_dns`), конфиг byedpi, firewall и антивирус. 13
разделов, вывод словами в разделах 8 и 13, результат — `netstat-report.txt`.

Ничего не меняет: только чтение. Занимает 1–2 минуты.

Главное, что он умеет: различает блокировку и **подмену DNS**. Признак подмены —
несколько не связанных между собой доменов разрешаются в один и тот же IP.

## Подмена DNS: `DNSFIX.bat`

Если `DIAG.bat` или `NETSTAT.bat` сказал, что резолвер провайдера отдаёт
адрес заглушки — это лечится одной командой:

```bat
DNSFIX.bat
```

В окне будет три шага `[1/3] [2/3] [3/3]` и **одно** окно UAC — ровно на одно
действие: перенести подготовленный файл hosts на место. Всё остальное считается
без прав, в обычном окне, где вывод видно. Окно не закроется молча ни при каком
исходе: в конце `pause`, а всё, что печатал Python, лежит в `dnsfix-log.txt`.
Дальше скрипт сам:

| Шаг | Что делает |
|---|---|
| 1 | Пробует 12 DoH и 5 DoT и оставляет живые **именно у тебя**. Заранее рабочего адреса нет: с августа 2026 операторы в РФ начали резать DoH/DoT, и Яндекс DoH в замерах не отвечал вовсе |
| 2 | Спрашивает каждый домен у системного резолвера, трёх UDP-резолверов и всех живых DoH одновременно |
| 3 | Берёт настоящий адрес **консенсусом** независимых зарубежных DoH |
| 4 | Проверяет связь по настоящему адресу: TCP → TLS с верным SNI → HTTP, отдельно HTTPS и HTTP |
| 5 | Пишет адреса в `hosts` помеченным блоком (копия прежнего файла рядом), ставит рабочий DoH в Firefox через `user.js`, включает `network.proxy.socks_remote_dns` |
| 6 | Сбрасывает кэш DNS и **перепроверяет всё заново** |
| 7 | Пишет словами: что было, что стало, что делать дальше |

Результат — `dnsfix-report.txt` (разделы 7–8 **дописываются в тот же файл**, слать
надо один). Откат — `DNSFIX.bat --revert`, проверен побайтово (тесты `9f[crlf]`
и `9f[lf]`). Если права не выдать — лечение не применится, но отчёт соберётся
целиком, а раздел 8 напечатает настоящие адреса и семь шагов, как вставить их
в hosts руками.

**Почему это первый шаг, а не последний.** byedpi, ciadpi и zapret маскируют
содержимое пакетов, но TCP-соединение устанавливается на адрес, который сказал
резолвер. При подмене соединение идёт на заглушку — и никакие аргументы десинка
это не починят. Домены для проверки берутся из прежних отчётов, поэтому порядок
`DIAG.bat` → `NETSTAT.bat` → `DNSFIX.bat` имеет смысл: каждый следующий
подхватывает то, что нашёл предыдущий.

Подробности — в `DNSFIX.md`.

## Многоканальная схема: `SYNTH.bat`

Если одного канала мало — нужен набор **независимых** каналов разной природы и автоматика,
которая выбирает живой. Одна команда:

```bat
SYNTH.bat
```

| Шаг | Что делает |
|---|---|
| 1. `synth.py --lib4u` | качает все источники подписок, сливает в один пул, отбрасывает дубли, меряет доступность, генерирует `synth/mihomo.yaml` и `synth/channels.txt` |
| 2. `yamlcheck.py` | валидирует профиль, чтобы Mihomo не подавился |
| 3. `orchestrate.py` | определяет **режим блокировки** и говорит, какой эшелон включать |

### Зачем нужен диспетчер

Три разных отказа в браузере выглядят одинаково — «не открывается», — а лечатся
взаимоисключающими способами:

| Белый сайт | Чёрный сайт | Чёрный через прокси | Режим | Действие |
|:---:|:---:|:---:|---|---|
| ✅ | ✅ | — | **A0** блокировки нет | ничего не делать |
| ✅ | ❌ | ✅ | **A** обычная блокировка | byedpi: `fix.bat`, `pick_multi.py` |
| ✅ | ❌ | ❌ | **B** белые списки | byedpi бессилен → `synth/mihomo.yaml` |
| ❌ | ❌ | ❌ | **C** рубят широко | DNS/сеть, затем SlipNet и Tor |

`orchestrate.py --watch 120` — дежурный режим: печатает `!!! СМЕНИЛСЯ РЕЖИМ`, когда
картина поменялась (мобильный интернет рубят волнами, это ловится автоматически).

### Эшелоны

| Эшелон | Природа | Почему здесь |
|---|---|---|
| 0 | **свои серверы** (`synth/sources.txt`) | единственное, чему можно доверять и что не выжгут |
| 1 | xhttp через CDN | у CDN много входных точек — блокировать придётся весь CDN |
| 2 | WebSocket | классика |
| 3 | gRPC / прямой TCP | запасные |
| 4 | **UDP (Hysteria2)** | другая стихия: если режут TCP, UDP может пройти |

Внутри эшелона Mihomo выбирает лучший по задержке (`url-test`), между эшелонами работает
`fallback`, а `tcp-concurrent: true` пробует несколько каналов одновременно.

**Честное ограничение:** проверить туннель средствами Python нельзя — VLESS/REALITY требуют
своего протокольного рукопожатия поверх TLS. Поэтому `synth.py` меряет только TCP-соединимость
и TLS-рукопожатие, а непроверенные каналы **не выбрасывает**, а сортирует: окончательный
вердикт даёт `url-test` внутри Mihomo. Подробности и остальные ограничения — в `SYNTH.md`.

## HTTP/3 (QUIC)

QUIC через SOCKS5 **не туннелируется**. Если HTTP/3 оставить включённым, Firefox либо
безуспешно долбится в QUIC и откатывается на HTTP/2 (лишние задержки на каждом сайте),
либо пробует прямой UDP на alt-svc адрес уже мимо прокси.

Поэтому `install.sh` / `install.bat` **по умолчанию** пишут в `user.js` профиля:

```js
user_pref("network.http.http3.enable", false);
user_pref("network.dns.http3_echconfig.enabled", false);
```

Блок помечен маркерами `/* byedpi-firefox:begin|end */` и убирается через `--uninstall`.
Отказаться от правки `user.js`: `--no-userjs`. `user.js` читается только при старте
Firefox — нужен **один перезапуск** браузера.

Расширение проверяет, применилось ли это на самом деле (`host/install.py:http3_state()`
смотрит и `user.js`, и фактический `prefs.js`), и показывает одну короткую подсказку,
если нужен перезапуск. Состояния: `off` · `pending_restart` · `on` · `unknown`.

## Установка

```bash
./install.sh            # Linux / macOS: ciadpi + native-хост + расширение + HTTP/3 off
./install.sh --simple   # то же, но ставить «простое» расширение
install.bat             # Windows
```

Расширение ставится этим же шагом — подписанный `.xpi` кладётся в
`<профиль>/extensions/`, остаётся перезапустить Firefox. Отключить: `--no-extension`.

> После распаковки архива Python-ом (а не `unzip`) бит исполнения теряется —
> тогда `bash install.sh` вместо `./install.sh`.

Подробности и ручная установка: [INSTALL.md](INSTALL.md).

## Сборка и тесты

```bash
python3 tools/build_xpi.py            # dist/*.xpi + release/*-installer.zip (полная версия)
python3 tools/build_xpi.py --simple   # то же для simple/
python3 host/ctl.py doctor            # вся диагностика одной командой
python3 tests/run_all.py              # все наборы (JS + четыре Python-модуля)
./tools/amo_sign.sh --lint            # линтер addons.mozilla.org
```

Каждый архив после сборки перечитывается и сверяется с исходниками по размеру,
CRC32 и SHA-256. Состав и статус сборки — в [REPORT.md](REPORT.md).

Набор `tests/test_30_tunnel.py` частично требует необязательного `curl_cffi`: без него
тесты Chrome-транспорта пропускаются, а не падают. Чтобы покрыть и их:

```bash
python3 -m venv /tmp/tunnel-venv && /tmp/tunnel-venv/bin/pip install curl_cffi
BYEDPI_PY=/tmp/tunnel-venv/bin/python python3 tests/run_all.py
```

## Требования

- Firefox 109+ (MV3 и `browser.proxy.settings`)
- Python 3.8+
- `ciadpi` — лежит в `bin/`, иначе скачивается `host/download_ciadpi.py`
- для `transport=tunnel`: свой сервер с доменом и TLS-сертификатом;
  `curl_cffi` желателен (отпечаток Chrome), но не обязателен

Разрешения расширения: `nativeMessaging` (связь с локальным хостом), `proxy` (прописка
SOCKS5 в Firefox), `storage` (запомнить положение переключателя), `alarms` (держать
event-page живым и раз в минуту проверять состояние). Доступ к сайтам не запрашивается,
данные никуда не отправляются — в манифесте заявлено `data_collection_permissions: ["none"]`.
